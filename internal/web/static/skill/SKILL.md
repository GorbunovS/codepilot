# CodePilot — RAG-поиск по коду

В проект подключён MCP-сервер codepilot с предпостроенным индексом кода
(BM25 + векторный поиск + гибридный реранк). Используй его инструменты
**вместо** grep и чтения файлов целиком — это сильно экономит контекст.

## Сначала: выбери проект

Сервер обслуживает **несколько проектов**. Вызови `list_projects` — получишь
список `{name, path, is_default}`. Дальше передавай имя нужного проекта
в аргументе `project` каждого инструмента. Пустой `project` — проект по
умолчанию (`is_default: true`).

**Если выдача явно про другой код** (чужие пакеты, несуществующие в твоей
задаче сущности, другой домен) — скорее всего запрос ушёл не в тот проект:
проверь `list_projects` и повтори с правильным `project`. Если нужного
проекта нет в списке — скажи пользователю добавить его в панели codepilot,
а сам временно работай обычными инструментами.

Ошибка «проект не найден; доступные: …» — исправь `project` на имя из
списка и повтори вызов, сервер перезапускать не нужно.

## Как формулировать запрос (важно для качества)

`search_code` — не полнотекстовый grep: реранкер (Laya) оценивает каждый
чанк на **соответствие запросу**, поэтому запрос должен описывать искомый
кусок кода, а не быть набором слов.

- Включай предметные существительные задачи: «подсветка шага обучения»,
  «расчёт скидки», а не «highlight node».
- Добавляй **критерии релевантности** — что искомый код обязан делать:
  «читает getBoundingClientRect целевого элемента и выставляет
  width/height оверлея». Чем конкретнее критерий, тем точнее реранк.
- Указывай ожидаемую форму кода, если знаешь: «CSS-класс оверлея»,
  «функция, вычисляющая позицию», «шаблон компонента».
- Один аспект за запрос. Лучше 2–3 точных запроса («геометрия подсветки»,
  «стили оверлея», «жизненный цикл шага tutorial»), чем один общий.
- Выдача нерелевантна — переформулируй запрос с другими критериями,
  а не повторяй тот же.

## Инструменты

Все инструменты принимают необязательный `project` (имя из `list_projects`;
пусто — проект по умолчанию).

- `list_projects` — список проектов сервера и проект по умолчанию.
- `search_code` — главная точка входа. Гибридный поиск по естественно-языковому
  запросу. Возвращает топ чанков с `file`, `start_line`, `end_line`, `symbol`,
  `score` и флагом `need_more`.
- `get_symbol` — определение символа (функция/тип/метод) по точному имени:
  файл, диапазон строк, сигнатура, doc. Используй, когда имя уже известно.
- `find_references` — все упоминания имени по проекту (список `file:line`).
  Используй для анализа использований и перед переименованием/рефакторингом.
- `read_span` — точные строки файла (1-based, включительно). Дочитка контекста
  по координатам из `search_code`/`get_symbol`.
- `reindex` — запуск инкрементальной переиндексации проекта в фоне.
  См. «Завершение задачи».

## Завершение задачи (триггер переиндексации)

Когда работа над кодом закончена — пользователь подтвердил решение, или ты
сам считаешь задачу выполненной и код изменился, или пользователь просит
запушить изменения, — вызови:

```
reindex {"project": "<имя проекта>"}
```

Это фоновый инкрементальный пересчёт индекса: изменённые файлы попадут
в поиск, чтобы следующая задача работала со свежим индексом. Если файлы
не менялись — это дешёвый no-op. Менял несколько проектов — вызови для
каждого. Ошибка «индексация уже идёт» — просто пропусти, индекс уже
обновляется.

## Рабочий цикл

1. `list_projects` → выбери проект задачи, дальше передавай его в `project`.
2. Сформулируй вопрос с критериями (см. выше) и вызови `search_code` (не grep!).
3. Если `need_more: true` — контекста недостаточно: дочитай нужные чанки через
   `read_span` (координаты есть в каждом хите) или уточни запрос и повтори поиск.
4. Нужны детали реализации символа → `get_symbol`; места использования →
   `find_references`.
5. Читай файлы целиком только если индекс не дал ответа (например, не-кодовые
   файлы вне индекса).

## Поля ответа search_code

- Выдача адаптивно отрезана по релевантности: возвращаются только хиты,
  близкие к лучшему (шумовое плато скрыто). Хитов обычно 1–4, а не ровно
  `top_k` — это норма, а не потеря данных.
- `more_available: true` — выдача обрезана (top_k или фильтром). Если топ
  не подошёл — повтори запрос с `top_k` 8–10 или переформулируй.
- `need_more: true` — реранкер считает, что контекста мало: дочитай чанки
  через `read_span` или задай уточняющий запрос.
- `degraded: "rerank_timeout" | "rerank_busy"` — нейросетевой реранк не
  успел/был занят, порядок приблизительный (hybrid без Laya). Результатам
  пользоваться можно, но для точного порядка повтори запрос позже.

## Правила

- Не дублируй поиск grep'ом «на всякий случай» — доверяй выдаче, проверяй
  через `read_span`.
- Не проси большой `top_k` «про запас»: каждый чанк — токены твоего
  контекста. Расширяй выдачу (top_k 8–10) только когда топ не подошёл
  (`more_available: true` и релевантного ответа нет).
- При `need_more: false` топа результатов достаточно — не запрашивай лишнего.
- Не пытайся запускать codepilot с флагами или перенастраивать сервер —
  всё настраивается в панели codepilot; твоя зона — только аргументы
  инструментов.
- Если индекс устарел или отсутствует, скажи пользователю запустить индексацию
  в панели codepilot, а сам временно работай обычными инструментами.
